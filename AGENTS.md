# Repository guidance

## Purpose and layout

This repository compares .NET architectures through independent Chinook music store examples. Read the root `README.md`, `docs/domain.md`, and the affected example's README before changing an example. Use `docs/axes.md` and `docs/comparing-examples.md` for architectural context.

Examples are grouped by the question they answer:

- `01-code-organization/`: layers, clean architecture, vertical slices, CQRS, and event sourcing.
- `02-boundaries-and-distribution/`: modular monoliths, microservices, messaging, Orleans, and BFF gateways.
- `03-ui-delivery/`: Razor Pages with htmx, Blazor variants, and MAUI.
- `04-hosting-and-runtime/`: Aspire, Azure Functions, and worker services.
- `05-cross-cutting/`: multi-tenancy and strangler fig migration.

Each example has its own solution, `src/`, `tests/`, `Directory.Build.props`, and README. There is no root solution. Shared documentation lives in `docs/`; SQL Server setup and scripts live in `database/`.

## Architectural constraints

- Keep each example independently buildable and copyable. Do not introduce project references between examples or extract shared domain projects. Duplication is intentional so examples can use different entity shapes.
- Preserve the architecture demonstrated by the affected example, including dependency direction and module boundaries. Follow its existing data access approach and composition root.
- Treat `docs/domain.md` as the contract for use cases, invariants, schema mappings, and events. Map to actual Chinook column names; most primary keys are `Id`, while `PlaylistTrack` has a composite key.
- New examples must belong to one axis and implement the shared domain. Document omissions and their reasons in the example README.
- Many examples are scaffolds. Do not describe unimplemented use cases or placeholder tests as complete functionality or coverage.

## Build, test, and run

Use the .NET SDK selected by `global.json` (`10.0.100` with `latestFeature` roll-forward). Examples generally target `net10.0`; inspect the project for platform-specific targets. Example build properties enable nullable reference types, implicit usings, the latest language version, and warnings as errors.

Run these commands from the repository root, replacing the example paths as needed:

```bash
dotnet build 01-code-organization/clean-architecture-razor-pages/clean-architecture-razor-pages.sln -c Release
dotnet test 01-code-organization/clean-architecture-razor-pages/tests/Chinook.Clean.Tests/Chinook.Clean.Tests.csproj -c Release
dotnet run --project 01-code-organization/clean-architecture-razor-pages/src/Chinook.Clean.Web
```

- Build and run the relevant tests for the affected example. Tests use xUnit and live in each example's test project. Add meaningful behavior or boundary tests when changing functionality.
- For changes affecting multiple examples or shared build configuration, run `./build-all.sh` or `./build-all.ps1`. These scripts build in Release and respect `.skip-build` markers; they do not execute tests.
- GitHub Actions runs `./build-all.sh` with .NET 10 on Ubuntu. Builds require no running database; keep automated unit and architecture tests independent of SQL Server.
- The MAUI App has a project-level `.skip-build` marker because it requires platform workloads. The build scripts still build its API and tests. Keep the marker unless the App has been successfully validated with the required workloads and platform SDKs. Directly building its entire solution can require those workloads.
- Use the affected README for startup projects, ports, and Aspire orchestration. Run `dotnet tool restore` inside an example when its local EF tools are needed.
- Documentation-only changes do not need a full .NET build. Check paths, commands, and the final diff instead. Report checks actually run and any limitations.

## Database workflow

Read `database/README.md` before changing database setup. To run an example against local SQL Server:

```bash
cd database
./start-db.sh
./init-db.sh --tenants US,EU
```

PowerShell equivalents are available. Tenant copies are needed for the multi-tenant example; ordinary examples use `Chinook`. Applications use `ConnectionStrings:Chinook`; additional databases and connection keys are documented in the database README.

- Do not edit `database/chinook_with_sprocs-id-pk.sql`, the canonical schema and seed script.
- `database/chinook.docker.sql` is generated by `database/generate-docker-sql.sh`. Make supported transformation changes in the generator and regenerate rather than editing the output by hand.
- Both SQL files are UTF-16LE with CRLF and marked binary in `.gitattributes`. Preserve their encoding and line endings.
- Keep event stores, messaging tables, and Orleans state in their dedicated databases rather than adding tables to `Chinook`.
- The documented development database password is deliberately public sample configuration. Keep real credentials out of source control, and keep SQL connection strings out of browser and native clients.
- Database initialization with `--force` drops and recreates databases; stopping through the provided stop script removes the container and its data. Do not use these destructive options as routine validation.

## Code and documentation conventions

- Follow `.editorconfig`: spaces, LF, final newline; four-space C# indentation and two-space JSON and XML project/config indentation. Preserve the SQL exceptions above.
- Prefer the configured C# conventions, including file-scoped namespaces, explicit local types, PascalCase types and methods, `I`-prefixed interfaces, and `_camelCase` private fields.
- Namespace roots follow `Chinook.<Architecture>.<Role>`; test projects follow `<Prefix>.Tests`. Match neighboring files and the example's project boundaries.
- Keep framework and dependency changes scoped to the request. Framework upgrades are intended to happen across the repository together.
- Keep example READMEs accurate about setup, data access, omissions, and status. Preserve their common explanatory sections: what this is, when to pick it, when not to, and what to inspect first.
- Keep changes focused and avoid unrelated formatting or generated build artifacts. Summarize changed behavior and validation in the handoff.
